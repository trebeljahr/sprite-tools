# JSON output schemas

The canonical shapes every tool emits, in one place. All metadata tools share a **header** (source, frame dims, grid) and add a **namespaced** field for their data, so you can merge outputs with `jq -s 'add'` without collisions.

## Common header

```ts
interface Header {
  source: string;         // filename (browser) or input path (CLI)
  sourceWidth?: number;   // pixel size of `source`
  sourceHeight?: number;
  frameWidth: number;
  frameHeight: number;
  grid: {
    cols: number;
    rows: number;
    detected: boolean;
    margin?: { left: number; top: number; right: number; bottom: number };
    spacing?: { x: number; y: number };
  };
}
```

Every `collision`, `pivot`, `tags`, `nine-slice`, `palette`, `meta` output starts with this.

`grid.margin` and `grid.spacing` are the [grid padding](/docs/cli/reference#grid-padding-margins-and-gutters) the frames were actually cut with, all zeros for a flush sheet. The CLI `collision`, `pivot`, `tags`, `meta` and `palette` commands, `slice --json`, and every MCP sheet tool report them. `sourceWidth`/`sourceHeight` come from the CLI `collision`, `pivot`, `tags`, `meta` and `palette` commands and the MCP `sprite_generate_collision`, `sprite_generate_pivot`, `sprite_generate_tags` and `sprite_generate_meta` tools. The exporter needs both on a padded sheet or one whose size is not a multiple of the cell size.

## Tags

```ts
interface TagsOutput extends Header {
  frameCount: number;
  tags: Array<{
    name: string;
    from: number;   // inclusive
    to: number;     // inclusive
    direction: "forward" | "reverse" | "pingpong";
    fps: number;
  }>;
  frameDurations?: Array<number | null>;   // ms per frame; null = use the tag's fps
}
```

### `frameDurations`

Optional. One entry per frame of the sheet, in **milliseconds**; when the field is present its length equals `frameCount`. `null` at index `i` means "frame `i` has no explicit hold" — whichever tag is playing it falls back to that tag's `fps`.

The key is omitted entirely when no frame has an explicit hold. An all-`null` array is never written, so a sheet can put a 250 ms hold on 2 frames of 40 without inventing numbers for the other 38.

**Backward compatible.** A document without `frameDurations` behaves exactly as it did before the field existed: every frame of a tag lasts `1000 / fps` ms, and every existing tags JSON keeps producing byte-for-byte identical output.

`fps` and `frameDurations` are not alternatives. `fps` stays the per-tag fallback rate for every frame in that tag with no explicit duration, which is what gives per-tag speed control without a duration array per tag.

```json
{
  "frameCount": 6,
  "tags": [
    { "name": "idle", "from": 0, "to": 5, "direction": "forward", "fps": 12 }
  ],
  "frameDurations": [250, null, null, 250, null, null]
}
```

Frames 0 and 3 are held for 250 ms. Frames 1, 2, 4, and 5 have no explicit hold, so they run at the tag's 12 fps — 83 ms each.

### Why durations are per frame, not per frame-per-tag

1. A frame is one drawing, and how long it wants to be on screen is a property of that drawing, not of whichever clip happens to include it. [Aseprite](https://www.aseprite.org/) — the tool this format interoperates with — stores duration on the frame for the same reason.
2. This document already models tags as ranges (`from`/`to`) over **one** global frame sequence. Two overlapping tags would each need their own copy of the durations for the shared frames, and the format has no way to express which copy wins when they disagree.
3. Tag-level `fps` already covers the per-clip case: it is the fallback rate for every frame in that tag without an explicit hold.

**Known limitation.** The same frame cannot be held for different lengths in two different tags — frame 3 is 250 ms whether "idle" or "full-cycle" is playing it. Workaround: duplicate the frame in the sheet so each clip gets its own index, and give the two indices different durations.

### Consuming durations

GIF export applies these durations per frame, but GIF stores delay in 10 ms units: a 125 ms hold is written as 130 ms, and anything under 20 ms is floored at 20 ms. See [GIF export](/docs/web/gif) for the details — the timing is close, not exact.

[`sprite-tools export`](/docs/reference/engine-export) reads `frameDurations` too: a hold becomes the frame's `duration` in milliseconds in Aseprite and Phaser/Pixi output, and a Godot per-frame `duration` multiplier against the animation's `speed` (250 ms at 12 fps is `3.0`). Unity `.meta` files have no timing field, so holds do not reach them.

## Nine-slice

```ts
interface NineSliceOutput extends Header {
  options: {
    auto: boolean;          // true when any inset was auto-detected
    explicit: { left?: number; right?: number; top?: number; bottom?: number } | null;
    alphaThreshold: number; // default 8
    tolerance: number;      // default 0.02, normalized 0..1
    minMiddle: number;      // default 1
    ninePatch?: boolean;    // true when insets came from a .9.png marker border
  };
  nineSlice: Array<{
    index: number;
    cell: { row: number; col: number };
    insets: { left: number; right: number; top: number; bottom: number };
    detected: boolean;   // false when nothing was guessed (all sides given, or from a .9.png)
    confidence: number;  // 0..1, 0 when nothing was guessed
    regions: Array<{
      name: string;      // "top-left" ... "bottom-right", row-major
      x: number; y: number; width: number; height: number;
      stretchX: boolean; stretchY: boolean;
    }>;
  }>;
}
```

`regions` is always nine entries in row-major order, and they tile the frame exactly — no gaps, no overlap. Corners have both stretch flags `false`, edges have exactly one `true`, the center has both. `insets` are clamped so the opposing pairs can never overlap. See the [Nine-slice page](/docs/web/nine-slice) for what `confidence` is worth and where the detector gives up.

## Meta (combined)

```ts
interface MetaOutput extends Header {
  frameCount: number;
  collision?:  CollisionOutput["collision"];   // present if --collision
  pivots?:     PivotOutput["pivots"];          // present if --pivot
  tags?:       TagsOutput["tags"];             // present if --tag was passed
  nineSlice?:  NineSliceOutput["nineSlice"];   // present if --nine-slice
  frameDurations?: TagsOutput["frameDurations"];   // present if any frame has an explicit hold
}
```

`frameDurations` mirrors the [Tags](#tags) shape exactly — global per frame, milliseconds, `null` for "use the tag's fps" — and sits at the top level next to `tags[]` rather than inside it. It is omitted when no frame has an explicit hold.

## Dedupe

```ts
interface DedupeOutput extends Header {   // grid is the INPUT grid
  frameCount: number;
  method: "exact" | "mae";        // "exact" when threshold is 0
  threshold: number;              // max mean RGBA difference, 0-255 scale, inclusive
  uniqueCount: number;
  removedCount: number;
  keptIndices: number[];          // old indices kept, ascending
  remap: number[];                // remap[oldIndex] = new index of its kept frame; length === frameCount
  groups: Array<{                 // only groups with at least one duplicate
    keep: number;                 // old index of the kept frame
    duplicates: number[];         // old indices removed, ascending
    distances: number[];          // distances[i] = MAE(duplicates[i], keep); 0 = byte-identical
  }>;
  tags?: Array<{                  // present when a tags file was passed
    name: string;
    from: number;                 // min(frames)
    to: number;                   // max(frames)
    direction?: string;           // copied from the input tag when present
    fps?: number;                 // copied from the input tag when present
    frames: number[];             // exact ordered new indices the tag plays — authoritative
    contiguous: boolean;          // false when frames is not exactly from..to
  }>;
  warnings?: string[];            // present when a tags file was passed
}
```

When `contiguous` is `false`, read `frames`, not `from`/`to`. threshold is the mean absolute difference per RGBA channel on a 0-255 scale, averaged over every channel of every pixel. 0 requires byte-identical frames. 1 means the average channel differs by 1/255 (~0.4%), the scale of rounding noise from lossy video compression or canvas alpha premultiplication. 2-4 absorbs a handful of stray pixels. Above ~8 visibly different poses start collapsing. See the [CLI reference](/docs/cli/reference#dedupe) for the full rules. The MCP tool returns the same fields plus `output`, `options`, and path fields, with `tags: null` and an always-present `warnings` array.

## Atlas manifest

```ts
interface AtlasManifest {
  atlas: string;      // PNG filename, e.g. "atlas.png"
  width: number;
  height: number;
  frames: {
    [spriteName: string]: {
      frame: { x: number; y: number; w: number; h: number };   // where in the atlas

      spriteSourceSize: { x: number; y: number; w: number; h: number };  // trimmed rect within original canvas
    };
  };
}
```

## Merging outputs

Because namespaces don't collide:

```bash
sprite-tools collision hero.png -o c.json
sprite-tools pivot    hero.png -o p.json
sprite-tools tags     hero.png --tag idle=0-5 --tag run=6-11 -o t.json
jq -s 'add' c.json p.json t.json > hero.json
```

`hero.json` ends up with `source`, `frameWidth`, `frameHeight`, `grid`, `options`, `frameCount`, `collision[]`, `pivots[]`, `tags[]` — a single sprite-metadata file ready for an engine.

The payload keys never collide, but `options` is a shared top-level key: the last file in the `jq -s 'add'` list wins it. If you care which command's `options` survives, put that file last, or use `sprite-tools meta` for a single pass instead.

## Feeding a document to an engine

That merged document is the input to `sprite-tools export` (and the `sprite_export_engine` MCP tool). The exporter accepts any of the shapes on this page:

- one command's output — `CollisionOutput`, `PivotOutput`, `TagsOutput`
- a `jq -s add` merge of several of them
- a `MetaOutput`
- an `AtlasManifest`
- a header merged with an atlas manifest, in which case the manifest's rects win and the header's tags/pivots/collision attach to them by index

Sections that are absent are skipped rather than defaulted, so a tags-only document still exports — it just produces animations over untrimmed grid cells with no pivots and no collision.

Two values the exporter resolves rather than copies:

- **Texture size** — for a header document, the size read from the `source` PNG when the file exists, else `sourceWidth`/`sourceHeight`. The grid is checked against that size, and a mismatch is an error. With neither, it falls back to `frameWidth × grid.cols` by `frameHeight × grid.rows` plus `grid.margin` and the `grid.spacing` gutters. For a manifest it is the manifest's own `width`/`height`. Unity's sprite rects are computed against that height, so a wrong `grid` mirrors the whole sheet vertically with no error.
- **Per-frame duration** — `round(1000 / fps)` of the first tag covering the frame, or of the `--fps` default for frames no tag covers.

See [engine export](/docs/reference/engine-export) for what each format does with the document, and where the conversions are lossy.
